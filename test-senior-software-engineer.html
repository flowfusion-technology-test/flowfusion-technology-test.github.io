FLOWFUSION TECHNOLOGY – Senior Software Engineer Code Challenge

This page describes the coding assignment for candidates applying as Senior Software Engineer at FlowFusion Technology.

Please read all requirements carefully and implement the assignment as if it were a real production service.

Goal: Build a backend service that manages the application process between Suppliers and Campaign Managers. The goal is to demonstrate a solid understanding of relational data modeling and RESTful API design.

1. Problem Overview

You will design and implement a backend service that handles:

  • Campaign Discovery – Suppliers can view available campaigns.
  • Application Submission – Suppliers apply to campaigns only during active registration periods.
  • Review Process – Campaign Managers can view pending applications and Approve or Reject them.
  • Resubmission (Bonus) – Rejected applications can be edited and resubmitted while the registration period is still open.

Use any SQL-based database and your preferred backend framework (e.g. Node/Express, Python/FastAPI, Go, etc.). Focus on clean schema design, clear API contracts, and proper state handling.

2. Functional Requirements

2.1 Campaign Discovery

Suppliers should be able to view available campaigns (e.g. list campaigns with active registration windows).

2.2 Application Submission

Suppliers can apply to a campaign only during its active registration_period. The server must validate that the submission falls within this window.

2.3 Review Process

Campaign Managers can view pending applications and either Approve or Reject them.

2.4 Resubmission (Bonus)

If an application is rejected, the Supplier should be able to edit and resubmit, provided the campaign’s registration period is still open.

3. Database Schema Design

Design a schema that tracks the lifecycle of an application while maintaining clear relationships.

Suggested Tables

Table Key Fields Description
Users id, role (Supplier/Manager), name System participants.
Campaigns id, title, start_date, end_date The "host" entities for applications.
Applications id, campaign_id, supplier_id, status, content Tracks the state (Pending, Approved, Rejected).
Audit_Log id, application_id, action, timestamp (Recommended) Tracks status changes for debugging.

You may extend these tables (e.g. registration_period fields on Campaigns, feedback on Applications) as long as the relationships and lifecycle are clear.

4. API Specification

Implement the following endpoints. Request/response formats can be adapted to your framework, but the behavior and semantics should match.

4.1 Supplier Endpoints

  1. List campaigns
    GET /campaigns
    List all campaigns with active registration windows (or all campaigns with filter options).

  2. Submit application
    POST /applications
    Submit a new application.
    Validation: Ensure the supplier has not already applied to the same campaign (unless resubmitting a rejected application—see your resubmission strategy).

  3. Update / Resubmit application
    PUT /applications/{id}
    Update or resubmit a rejected application. Only allowed when the campaign’s registration period is still open.

4.2 Manager Endpoints

  1. List applications
    GET /manager/applications
    List applications filtered by status (e.g. ?status=pending).

  2. Change application status
    PATCH /applications/{id}/status
    Transition the application state.
    Payload: { "status": "approved" | "rejected", "feedback": "Optional text" }

5. Candidate Instructions

5.1 Your Task

  • Implement the database schema using any SQL-based dialect (PostgreSQL, MySQL, SQLite, etc.).
  • Develop the API logic using your preferred backend framework (Node/Express, Python/FastAPI, Go, etc.).
  • State machine logic: Ensure an application cannot move from Approved back to Pending without specific triggers (define and document your rules).

5.2 Constraints

  • Suppliers cannot approve their own applications (enforce role checks).
  • Applications submitted after the campaign’s end_date (or after registration period end) must be blocked by the server (e.g. 400 Bad Request with a clear message).

5.3 Resubmission Strategy

Decide and document how resubmission works:

  • Does it overwrite the existing application record (same id, updated content/status)?
  • Or do you maintain version history (e.g. new row or version table)?

Either approach is acceptable; consistency and clarity in your README will be evaluated.

6. Evaluation Criteria

  • Clean code – Modularized logic, proper error handling (e.g. 400 Bad Request for expired deadlines, 403 for unauthorized actions).
  • Consistency – How you handle resubmission (overwrite vs version history) and that it is clearly documented.
  • Security – Basic role-based access control (RBAC) simulation (Suppliers vs Managers; no self-approval).
  • Data model – Sensible tables, keys, and relationships; optional use of Audit_Log for traceability.

7. Project Setup & Deliverables

Your repository should include at least:

  1. Source code – Schema (migrations or SQL scripts) and API implementation.
  2. A clear README.md with:
    • Project overview and how to run the service
    • Database setup (e.g. create DB, run migrations)
    • Example API requests (e.g. curl or Postman examples)
    • Resubmission strategy and state machine rules
    • Any design decisions or trade-offs
  3. Configuration – e.g. .env.example for database URL and any secrets.
  4. Bonus: docker-compose.yml to run the app and database locally.

We should be able to run the service locally and call the documented endpoints successfully.

8. Submission Guidelines

  • Host your solution in a Git repository (GitHub, GitLab, or similar).
  • Ensure the repository is accessible to our team.
  • Include all required instructions in README.md so we can build, run, and understand your design.

Please follow the submission channel or instructions provided by the recruiter or job posting.
